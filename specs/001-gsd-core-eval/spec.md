## User Stories

### User Story 1 (US1): Deterministic external gate proven live (criterion a)
**As a** pipeline maintainer, **I want to** prove gsd's `workflow.test_command` blocks phase
advancement on a failing external command and proceeds on a passing one, **so that** FFS's
deterministic gates (gates.py / runtime_proof) can be enforced inside gsd.

**Acceptance Criteria:**
- [ ] `gate.sh` exit 1 → gsd BLOCKS advancement, `WAVE_FAILURE_COUNT` increments (STATE.md before-snapshot + transcript)
- [ ] `gate.sh` flipped to exit 0 → gsd proceeds (STATE.md after-snapshot)
- [ ] STATE.md confirms the run actually reached the post-merge build/test gate; short-circuit before the gate = INCONCLUSIVE = FAIL

### User Story 2 (US2): Model overrides honored (criterion b)
**As a** cost-conscious operator, **I want to** verify `model_overrides.<agent>` in
`.planning/config.json` changes the OBSERVED model of spawned agents, **so that** the
haiku/sonnet/opus routing ladder survives adoption.

**Acceptance Criteria:**
- [ ] Observed model = `message.model` in subagent transcript JSONL (config contents do not count)
- [ ] ≥1 of opus/sonnet/haiku override classified APPLIED (requested==observed)
- [ ] Every attempt classified exactly one of APPLIED / WRONG-MODEL / NO-SPAWN / IGNORED
- [ ] Bonus recorded: fully-qualified `fable-5` ID accepted or ignored

### User Story 3 (US3): Executor commit discipline proven (criterion c)
**As a** repo owner with scoped-git-add discipline, **I want** command-level proof the gsd
executor never uses `git add -A`/`add .`/`--all` and never pushes, **so that** adoption cannot
corrupt branches.

**Acceptance Criteria:**
- [ ] git PATH shim argv log contains zero `add -A`/`add .`/`add --all` and zero `push`
- [ ] Every logged `add` names explicit paths
- [ ] `git for-each-ref refs/remotes` empty, `git remote -v` empty, per-commit path lists consistent with feature files

### User Story 4 (US4): Subagent env-fit (criterion d)
**As a** operator on a machine with ~190k-token subagent bootstrap, **I want to** record whether
gsd's Claude Code subagent spawns complete or overflow the 200k window, **so that** a known
environment blocker is scored before any port work.

**Acceptance Criteria:**
- [ ] Spawn success/failure captured with any overflow error text
- [ ] Failure = documented NO-GO reason for Phase 1

### User Story 5 (US5): Enforcement port design (Phase 1, gated on US1+US3+US4 pass)
**As a** FFS maintainer, **I want** a concrete design mapping FFS enforcement onto gsd,
**so that** migration keeps machine completion authority.

**Acceptance Criteria:**
- [ ] Mapping table: gates.py evidence store keyed off `.planning` artifacts; checkbox-evidence-gate.sh re-keyed to `.planning/STATE.md`; `runtime_proof.py verify` as `workflow.test_command`; gates.py grant/check-grant (existing shipped semantics, reused verbatim) around gsd ship stage
- [ ] gsd parallel-run on one small real FFS feature in a throwaway branch/worktree, no push

### User Story 6 (US6): Go/No-Go recommendation
**As a** the operator, **I want** report.md opening with a one-line GO/NO-GO plus an a/b/c/d
criteria table with evidence refs, **so that** the adoption decision is evidence-backed.

**Acceptance Criteria:**
- [ ] `spike-results/gsd-core-eval/report.md` opens with GO or NO-GO one-liner
- [ ] Criteria table a/b/c/d with per-criterion evidence file references
- [ ] Installed gsd version pinned and cited next to every doc claim

## Constraints

- Spike runs ONLY in `mktemp -d` sandbox outside the repo; repo receives docs-only curated evidence copies at phase end
- Python 3.11 stdlib-only glue; Node/npx required in sandbox
- No pushes, no merges, no FFS skill migration/removal (operator-gated)
- Model routing: haiku=scout, sonnet=build, opus=adversarial verify; Fable orchestrates only
